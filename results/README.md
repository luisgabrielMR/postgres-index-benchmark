# Results

This folder stores local benchmark outputs generated by the execution scripts.

Generated files:

- `before-index.txt`: `EXPLAIN (ANALYZE, BUFFERS)` before the composite index.
- `after-index.txt`: `EXPLAIN (ANALYZE, BUFFERS)` after the composite index.
- `summary.csv`: execution time values extracted from the PostgreSQL output.
- `resource-summary.csv`: resource indicators extracted from the PostgreSQL output.
- `benchmark-results.png`: optional dashboard chart generated with Python.
- `execution-time-comparison.png`: compatibility copy generated with Python.

## Observed In This Local Run

Before index plan summary: PostgreSQL used a `Parallel Seq Scan` on `orders`, then a `Sort` with `top-N heapsort` for `created_at DESC`.

After index plan summary: PostgreSQL used `Index Scan using idx_orders_customer_status_created_at`.

Execution time before index: `341.939 ms`.

Execution time after index: `43.730 ms`.

Observed scan change, if any: `Parallel Seq Scan` changed to `Index Scan`.

Resource observations:

| Scenario | Shared hits | Shared reads | Rows removed by filter | Sort memory | Workers launched |
| --- | ---: | ---: | ---: | ---: | ---: |
| Before index | `5449` | `0` | `166333` | `27 kB` | `2` |
| After index | `1` | `3` | `0` | `0 kB` | `0` |

These resource indicators come from `EXPLAIN (ANALYZE, BUFFERS)`. They are PostgreSQL plan-level indicators, not operating-system CPU or container memory measurements.

Short conclusion: in this specific query and dataset, the composite index helped PostgreSQL find the target rows much faster. This does not mean every index improves every query.
